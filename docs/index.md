<header><div class="hero"><div class="eyebrow">FlyRank ML Internship Capstone</div><h1>Ranking Content Pages for Engagement Opportunity Investigation</h1><p class="hero-description">Using search and engagement signals to prioritize content pages for human investigation and possible improvement.</p></div></header>
<main class="container">
<section id="abstract"><h2>1. Title + Abstract</h2><div class="abstract"><p>This study asks which content pages a website manager should investigate first when they show potential engagement problems. Using the FlyRank ML Internship warehouse release, the analysis focuses on 9,841,378 daily content-performance observations from March 2026, covering 55 clients and 331,437 content pages. A Random Forest model was used to rank pages from observed search and engagement signals, with validation performed using a client-grouped split and Precision@50 as the primary ranking metric. The Random Forest achieved a Precision@50 of 0.70 compared with 0.00 for the Week-4 rule-based baseline on the same held-out test set. The resulting ranking is intended as decision support that helps website managers prioritize pages for investigation and possible improvement rather than automatically determining what changes should be made.</p></div></section>
<section id="introduction"><h2>2. Introduction / Problem Statement</h2><p>Website managers may have a large number of content pages competing for limited review time. The practical question is therefore not simply whether a page has an engagement problem, but which pages should be investigated first.</p><p>This capstone addresses the following research question:</p><div class="metric-card"><strong>Which content pages should a website manager investigate first when they show potential engagement problems?</strong></div><p>The decision supported by this analysis is the prioritization of pages for investigation and possible improvement.</p><p>The output is a ranked list of content pages based on an engagement-opportunity score. A human website manager can use this ranking to decide where to begin investigation, while retaining responsibility for diagnosing the cause of a problem and choosing an appropriate action.</p><p>Machine learning is useful here because multiple observed search and engagement signals may interact in ways that are difficult to capture with a single hand-written rule. The model therefore provides a systematic way to combine these signals into a prioritization score.</p><p>The cost of a wrong call is also important. A page ranked too highly may receive unnecessary review effort, while a page ranked too low may have a potential engagement issue overlooked. For this reason, the model is framed as decision support, not as an automatic content-change system.</p></section>
<section id="data"><h2>3. Data</h2><p>This analysis uses the public-safe FlyRank ML Internship warehouse release hosted on Hugging Face. The analysis uses the <strong>fact_content_daily_performance</strong> table and focuses on the March 2026 development window.</p><div class="stats"><div class="stat"><strong>9,841,378</strong>March daily observations</div><div class="stat"><strong>55</strong>clients</div><div class="stat"><strong>331,437</strong>content pages</div><div class="stat"><strong>March 2026</strong>development window</div></div><p>The March 2026 data covers dates from March 1, 2026 through March 31, 2026. For modeling, the daily observations were aggregated to one row per client and content page.</p><h3>Modeling signals</h3><ul><li>gsc_impressions</li><li>gsc_clicks</li><li>avg_position</li><li>sessions_ai</li><li>scroll_events</li></ul><p>The analysis deliberately excludes future-month performance so that information from periods after the development window does not influence the ranking.</p><p>Client and content identifiers are pseudonymous. They are retained only where needed for grouping, evaluation, and traceability and are not used as predictive features.</p><p>The public-facing work does not expose client names, domains, URLs, private queries, credentials, or raw data exports.</p><p>Data-availability fields were also excluded as predictive signals because they describe whether data exists rather than representing the engagement behavior that the model is intended to rank.</p><p>The March 2026 development window was selected based on the earlier data-contract and baseline work. The analysis is therefore scoped to the observed March 2026 data rather than making claims about all future periods.</p></section>
<section id="methodology"><h2>4. Methodology</h2><p>This analysis treats engagement opportunity as a ranking problem rather than a classification problem. The objective is to produce an opportunity score that helps prioritize pages for human investigation.</p><h3>Model</h3><p>A Random Forest was selected because it can capture nonlinear relationships and interactions among multiple observed search and engagement signals. The model produces a ranking score for prioritization rather than an automatic decision about whether a page should be changed.</p><p>The model uses five features:</p><ul><li>gsc_impressions</li><li>gsc_clicks</li><li>avg_position</li><li>sessions_ai</li><li>scroll_events</li></ul><h3>Engagement-opportunity proxy</h3><p>In the evaluation, a page is treated as an opportunity when it has positive GSC impressions but zero GSC clicks.</p><div class="note">This proxy is used to evaluate the ranking and is not treated as an independently validated business outcome.</div><h3>Baseline</h3><p>The model was compared against the transparent Week-4 rule-based baseline using the same evaluation data and the same Precision@50 metric.</p><h3>Validation design</h3><p>Validation used a client-grouped split. Clients were separated between the training and evaluation sets so that content from the same client did not appear in both sets.</p><p>This provides a more honest test of whether the ranking approach can generalize to clients that were not present in model training.</p><h3>Leakage checks</h3><p>Future-month performance was not used as a modeling feature. Client identifiers were used only for grouping and evaluation, not as predictive features.</p><p>The analysis also excluded client names, domains, URLs, private queries, credentials, and data-availability flags from predictive modeling.</p></section>
<section id="results"><h2>5. Results</h2><p>The Random Forest was evaluated against the Week-4 baseline on the same client-grouped held-out test set using Precision@50.</p><div class="table-wrapper"><table><thead><tr><th>Method</th><th>Precision@50</th></tr></thead><tbody><tr><td>Week-4 baseline</td><td>0.00</td></tr><tr><td><strong>Random Forest</strong></td><td><strong>0.70</strong></td></tr></tbody></table></div><p>The Week-4 baseline identified 0 of its top 50 pages as opportunities under the evaluation proxy, while the Random Forest identified 35 of its top 50 pages.</p><div class="formula">0.70 × 50 = 35</div><p>The Random Forest therefore produced a substantially stronger top-50 ranking than the simple baseline on this test split.</p><p>This is an observed evaluation result against the defined proxy. It should be interpreted as directional evidence, rather than proof that 70% of the pages have genuine engagement problems in the real world.</p><h3>Precision@50 comparison</h3><figure><img src="assets/IMG-20260829-WA0019.jpg" alt="Random Forest versus Week-4 baseline Precision at 50 comparison"><figcaption>Precision@50 comparison between the Week-4 baseline and Random Forest.</figcaption></figure><h3>Feature importance</h3><p>The fitted Random Forest placed the greatest importance on search impressions and clicks when producing its ranking.</p><div class="table-wrapper"><table><thead><tr><th>Feature</th><th>Importance</th></tr></thead><tbody><tr><td>gsc_impressions</td><td>0.734</td></tr><tr><td>gsc_clicks</td><td>0.204</td></tr><tr><td>avg_position</td><td>0.056</td></tr><tr><td>scroll_events</td><td>0.004</td></tr><tr><td>sessions_ai</td><td>0.002</td></tr></tbody></table></div><figure><img src="assets/IMG-20260829-WA0020.jpg" alt="Random Forest feature importance chart"><figcaption>Feature importance from the fitted Random Forest.</figcaption></figure><p>Feature importance describes how the fitted model used the available signals. It should not be interpreted as evidence that any individual signal causes engagement outcomes.</p></section>
<section id="limitations"><h2>6. Limitations &amp; Honest Framing</h2><p>This analysis has several important limitations.</p><p>First, the engagement-opportunity target is a proxy based on observed engagement signals rather than an independently validated business outcome. Therefore, Precision@50 measures how well the model ranks pages against this proxy; it does not prove that the model identifies real-world engagement problems at the same rate.</p><p>Second, the development and evaluation data come from March 2026. The results describe the observed data in that development window and may not generalize to other months or future data.</p><p>Third, client-grouped validation reduces the risk of client overlap between training and evaluation, but the test set still represents a limited sample of clients.</p><p>Fourth, the model identifies pages that may deserve investigation. It does not determine the correct content change, guarantee an improvement, or establish that changing a page will improve its performance.</p><p>Finally, the analysis identifies associations in the available data. It does not establish causal relationships between individual signals and engagement outcomes, and it does not claim to explain or predict Google's algorithm.</p><div class="note"><strong>Observed:</strong> The Random Forest achieved a Precision@50 of 0.70 against the defined evaluation proxy.<br><br><strong>Measured:</strong> 35 of the model's top 50 ranked pages were opportunities under that proxy.<br><br><strong>Directional:</strong> The model performed better than the Week-4 baseline on this held-out test split.<br><br><strong>Decision-support:</strong> The ranking can help prioritize pages for human investigation, while the final diagnosis and content decision remain with the website manager.</div></section>
<section id="recommendations"><h2>7. Ranked Recommendations</h2><p>The model output is intended to help a website manager prioritize limited review time.</p><p>Pages with higher model scores should be investigated first, particularly when they combine strong search visibility with low click capture.</p><h3>Recommended action playbook</h3><ol><li><strong>Investigate high-priority pages.</strong> Start with pages receiving high model scores. Give additional attention to pages with substantial impressions but very few or zero clicks.</li><li><strong>Diagnose before changing.</strong> Review the page title, description, search-intent alignment, and content usefulness. The model ranking identifies where to look; it does not decide what change should be made.</li><li><strong>Use reason codes to guide review.</strong> <em>low_click_capture</em> indicates visible pages with little or no observed click activity. <em>review_engagement</em> indicates that the page should be reviewed before any action is taken.</li><li><strong>Monitor after intervention.</strong> If a page is changed, evaluate its later performance separately. Do not treat the model ranking as evidence that an intervention caused an improvement.</li></ol><h3>Top-ranked examples</h3><div class="table-wrapper"><table><thead><tr><th>Rank</th><th>Content ID</th><th>Impressions</th><th>Clicks</th><th>Model Score</th><th>Recommended Action</th></tr></thead><tbody><tr><td>1</td><td>content_713b157e9c77690a</td><td>24,908</td><td>0</td><td>22,596.89</td><td>Investigate engagement</td></tr><tr><td>2</td><td>content_545bb6cc7081ded3</td><td>122,905</td><td>287</td><td>15,197.58</td><td>Review before action</td></tr><tr><td>3</td><td>content_d2eb49b1f5f3fa34</td><td>14,482</td><td>0</td><td>14,755.31</td><td>Investigate engagement</td></tr><tr><td>4</td><td>content_4002467a580a7f98</td><td>11,973</td><td>0</td><td>12,173.97</td><td>Investigate engagement</td></tr><tr><td>5</td><td>content_dc91779c3d085398</td><td>25,625</td><td>1</td><td>11,886.31</td><td>Review before action</td></tr></tbody></table></div><div class="workflow">Rank → Investigate → Diagnose → Act → Monitor</div><p>The ranking is decision support, not an automatic content-change system.</p></section>
<section id="reproducibility"><h2>8. Reproducibility</h2><p>The analysis was developed in Google Colab using Python, DuckDB, pandas, NumPy, and scikit-learn, with the FlyRank warehouse accessed through Hugging Face.</p><p>The development window was March 2026. The Random Forest used <strong>random_state=42</strong>, and the client-grouped train/test split also used <strong>random_state=42</strong>.</p><h3>Modeling workflow</h3><ol><li>Load the March 2026 warehouse data through DuckDB.</li><li>Aggregate daily observations to one row per client and content page.</li><li>Separate clients into training and test groups.</li><li>Train the Random Forest using the selected search and engagement features.</li><li>Compare the model with the Week-4 baseline using Precision@50.</li><li>Generate feature-importance and ranked-recommendation outputs.</li></ol><p>The capstone notebook and supporting assignment notebooks are stored in the repository under <strong>work/</strong> and <strong>notebooks/</strong>.</p><p>The analysis uses hashed identifiers for grouping and traceability. No client names, domains, URLs, private queries, credentials, or raw exports are included in the public-facing paper.</p><p>The reported results and artifacts in this paper correspond to the completed analysis notebook and recorded evaluation outputs.</p></section>
